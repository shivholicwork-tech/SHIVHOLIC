# AI SEO Agent SaaS Platform - Greenfield Implementation

An AI-powered SEO platform built as a Turborepo monorepo with a NestJS backend, Next.js 14 frontend, Prisma ORM, and an agent orchestration system claiming 16 AI agents. The implementation delivers a structurally complete scaffold: well-typed shared packages, a proper database schema with 18 models, a functional frontend with 11 pages running on mock data, and a backend wired with auth, billing stubs, and a BullMQ task queue. The architecture is sound in shape but soft on substance - the agent orchestration, billing, and AI integrations are mocked, and the security surface has several gaps that would bite in production.

**Watch for:** JWT secrets default to hardcoded strings in code and refresh tokens have no revocation mechanism (confirmed). The Stripe webhook guard validates only header presence, not actual signature verification (confirmed). No authorization layer exists - any authenticated user can access any project or team resource (confirmed). The `ChatService` uses an in-memory Map that loses all data on restart and grows unboundedly (confirmed).

## High-level view

The monorepo structure is well-organized with proper workspace dependencies, Turborepo task pipeline configuration, and a global Prisma module. The build chain works: shared types and database client are exported correctly, the API consumes workspace packages, and the frontend builds with correct path aliases.

Authentication implements JWT access/refresh token flows with bcrypt password hashing, but relies on hardcoded default secrets, has no token revocation, and the frontend auth route bypasses the NestJS backend entirely with a mock handler that returns fake tokens. The refresh endpoint accepts any string body parameter without validation.

The agent orchestration system is well-designed as an abstract pattern - registry, base class, typed I/O, BullMQ queue processing - but only 4 of 16 declared agents are implemented and all return hardcoded mock data. The agents never self-register with the `AgentRegistry`, so the registry stays empty at runtime.

The frontend is the most complete layer: properly structured with Zustand stores, React Query hooks, mock data, and polished UI with animations and responsive layout. However, all pages run entirely on client-side mock data with no actual API integration, and the dashboard layout is entirely client-rendered with no SSR benefit from Next.js 14.

Authorization is completely absent. Every endpoint that takes a `projectId` or `teamId` fetches the resource without checking whether the authenticated user belongs to that team. The `ProjectsController` takes `teamId` as a query parameter from the client, trusting it without verification.

<details>
<summary>Issues (9)</summary>

1. **Hardcoded JWT secrets** — `default-jwt-secret` and `default-refresh-secret` are fallback values baked into code. Remove defaults and fail fast if env vars are missing.
2. **No token revocation** — Refresh tokens are stateless JWTs with no blocklist. A leaked refresh token is valid for 7 days with no way to invalidate it. Implement a stored token approach or at minimum a token version/family check.
3. **Stripe webhook signature not verified** — `StripeWebhookGuard` checks only for header presence. Use `stripe.webhooks.constructEvent()` to actually verify the payload signature.
4. **No authorization / tenant isolation** — Any authenticated user can read/modify any project, team, or audit by guessing IDs. Add ownership checks to all resource-accessing services.
5. **Agent registry never populated** — Agents are instantiated by NestJS DI but never call `registry.register()`. The orchestration system is inert at runtime.
6. **In-memory chat storage** — `ChatService` stores conversations in a `Map` that is lost on restart and grows without bound. Replace with database persistence.
7. **Frontend auth route returns fake tokens** — `apps/web/src/app/api/auth/[...nextauth]/route.ts` returns a mock JWT without contacting the backend, creating a parallel unauthenticated path.
8. **Frontend response shape mismatch** — The API wraps all responses in `{ success, data, error }` via `TransformInterceptor`, but frontend hooks expect unwrapped response shapes. No hook unwraps `data` from the envelope.
9. **No test coverage** — Zero test files exist across the entire monorepo. No unit tests, no integration tests, no e2e tests.

## JWT secret management and token lifecycle

The `AuthService` and `JwtStrategy` both fallback to `'default-jwt-secret'` when `JWT_SECRET` is unset:

```typescript
secretOrKey: configService.get<string>('JWT_SECRET', 'default-jwt-secret'),
```

This means the application boots successfully without any configuration, signing tokens with a predictable secret. In a deployment where `.env` is misconfigured or missing, every token is forged trivially.

The refresh token flow is entirely stateless. `refreshToken()` verifies the JWT signature and issues new tokens, but there is no mechanism to revoke a refresh token - no stored token table, no family rotation, no version counter on the user record. A compromised refresh token grants access for its full 7-day lifetime. The `refresh` endpoint also accepts the token as a raw `@Body('refreshToken')` string with no DTO validation, so empty or malformed payloads reach the verify call and throw a generic "Invalid refresh token" error rather than a proper validation response.

## Stripe webhook signature bypass

```typescript
// stripe-webhook.guard.ts
canActivate(context: ExecutionContext): boolean {
  const signature = request.headers['stripe-signature'];
  if (!signature) throw new BadRequestException('Missing stripe-signature header');
  const webhookSecret = this.configService.get<string>('STRIPE_WEBHOOK_SECRET');
  if (!webhookSecret) throw new BadRequestException('Stripe webhook secret not configured');
  // For now, just validate the signature header exists
  return true;
}
```

Any request with a `stripe-signature` header passes the guard regardless of content. The commented intention to use `stripe.webhooks.constructEvent` is insufficient as shipped code - an attacker can trigger subscription state changes by sending arbitrary payloads to `/api/billing/webhook`.

Additionally, the webhook endpoint is marked `@Public()` (bypassing JWT auth) which is correct for Stripe webhooks, but combined with no signature verification, it's an open mutation endpoint.

## Missing authorization and tenant isolation

The `ProjectsController` requires JWT authentication via `@UseGuards(JwtAuthGuard)`, but `findAll()` accepts `teamId` as a client-supplied query parameter:

```typescript
@Get()
async findAll(@Query('teamId') teamId: string, ...) {
  return this.projectsService.findAll(teamId, ...);
}
```

No check verifies the authenticated user is a member of `teamId`. The same pattern repeats across `AuditController`, `ContentController`, `KeywordsController`, and `ChatController` - resources are fetched by ID without any ownership validation. The `CurrentUser` decorator extracts `{ sub, email }` from the JWT but services never use it to scope queries.

This means user A can enumerate and access user B's projects, audits, content, and keywords by iterating IDs - a classic IDOR vulnerability.

## Agent registry is never populated

The `AgentsModule` declares `AgentRegistry`, `SeoAuditAgent`, `KeywordResearchAgent`, `ContentWriterAgent`, and `AiChatAgent` as providers. NestJS will instantiate all of them, but none of the agent classes call `registry.register(this)`. The `AgentsService.runSingleAgent()` calls `this.registry.get(agentType)` which will always return `undefined`, causing a `NotFoundException` for every agent execution request.

The fix requires either an `OnModuleInit` hook in each agent that self-registers, or a factory in `AgentsModule` that explicitly registers agents after instantiation.

## In-memory ChatService with unbounded growth

```typescript
private conversations: Map<string, Conversation> = new Map();
```

Every message sent creates or appends to a conversation stored in a process-local Map. In a multi-instance deployment, conversations are not shared. In any deployment, memory grows monotonically - there is no eviction, no TTL, no max-size. The `getConversations` method iterates the entire Map to filter by userId, which is O(n) over all conversations.

## Frontend-backend contract mismatch

The `TransformInterceptor` wraps every API response:

```typescript
map((data) => ({ success: true, data, error: null }))
```

But the frontend `apiClient` calls `JSON.parse(text) as T` directly - it never unwraps `.data` from the envelope. The `useLogin` hook expects `data.user` and `data.access_token` at the top level, but the actual response is `{ success: true, data: { user, accessToken, refreshToken }, error: null }`.

Additionally, the backend returns `accessToken` (camelCase) and `refreshToken`, while the frontend `AuthResponse` type expects `access_token` (snake_case). This mismatch means auth flow will fail at runtime when the frontend connects to the real backend.

## Dashboard rendering strategy

The entire dashboard layout is marked `"use client"` at the layout level, which forces all child pages into client-side rendering. Combined with the fact that every page uses `React.useState` and mock data directly, there is no server-side rendering happening anywhere in the dashboard. For an SEO platform, this is somewhat ironic but not blocking for a SaaS dashboard that sits behind auth.

The `DashboardLayout` wraps children in a `framer-motion` div that animates opacity/position on every navigation. This animation fires for all page transitions including back-navigation, which may feel redundant rather than intentional.

## Database schema quality

The Prisma schema is well-structured with appropriate indexes, cascading deletes, unique constraints, and relationship modeling. The `TopicalMapNode` self-referential relation for hierarchical content planning is a good design. `@@map` annotations provide clean table names.

One schema gap: there is no `Conversation` or `ChatMessage` model, despite the backend having a `ChatService` that manages conversations. This confirms the in-memory storage was a known shortcut rather than an oversight in schema design, but it means the chat feature has no persistence path without schema migration.

## Missing test infrastructure

The monorepo has zero test files. No Jest config, no test utilities, no mocks beyond the frontend mock-data layer. The `turbo.json` declares a `test` task that depends on `build`, but no package defines a test script that does anything. For a platform with auth flows, billing webhooks, and agent orchestration, the absence of tests means every behavior is verified only by manual inspection.
